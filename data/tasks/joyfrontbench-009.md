一级分类：网页 / 业务界面
二级分类：工作台

## 一、任务目标

请在指定目录中，从零开发一个可直接运行、可独立部署的“营销百宝箱”纯前端项目。

本项目仅实现前端，不接入真实后端或数据库。促销查询、工具路由、接口延迟、流式响应、异常和空数据等能力均通过本地模拟服务、异步函数和模拟数据实现。

页面展示与业务逻辑通过 Service 层分离，替换服务实现时无需重写页面组件。

## 二、项目边界

本项目从零创建，运行所需的源码、类型、常量、本地数据、模拟服务和工具函数均包含在最终项目中，不读取项目目录之外的文件。

站点、商品、促销和用户价格数据由项目内的静态 TypeScript 或 JSON 数据定义。相同参数每次查询得到相同的业务结果；当前时间只用于生成查询时间和模拟耗时，不影响商品、促销、价格及状态。

页面通过以下分层完成促销查询：

```text
React 页面与组件
        ↓
Tool Router
        ↓
Mock Stream Service
        ↓
Promotion Mock Service
        ↓
本地业务数据
```

页面与组件负责输入和展示；Tool Router 负责工具路由；Mock Stream Service 负责分段返回；Promotion Mock Service 负责查询本地业务数据。页面组件不得直接读取或筛选底层数据。

## 三、技术与交付要求

1. 使用 React、TypeScript、Vite 开发。
2. 使用稳定、常见的 React 生态组件库完成页面，优先使用 Ant Design；也可使用其他成熟组件库，但不得混用多个大型组件库。
3. 项目必须从零创建，不得依赖已有业务工程。
4. 项目必须能够通过以下命令启动：

```bash
npm install
npm run dev
```

5. 项目必须能够通过以下命令构建：

```bash
npm run build
```

6. 不允许依赖真实 HTTP 接口、数据库、登录系统、对象存储或其他远程业务服务。
7. 不允许将所有业务逻辑堆叠在单个组件中。必须拆分页面层、组件层、类型层、模拟数据层、Service 层和工具函数层。
8. 页面刷新后不要求保留历史会话。
9. 所有模拟数据均应存放在项目本地；商品、促销、价格、用户命中关系和查询状态不得随机变化。
10. 提供 README，说明安装、启动、构建、本地业务数据和可用查询参数。
11. 页面中的文本、按钮、错误提示和表格字段全部使用中文。
12. 输出完整项目代码，不要只输出局部代码片段或设计说明。

## 四、业务背景

营销百宝箱是面向营销运营、商品运营和研发支持人员的工具型工作台。

用户通过站点、SKU ID 和用户 PIN 查询：

1. 指定 SKU 在目标站点配置的全部促销；
2. 指定用户实际命中的促销；
3. 用户当前实时促销价格；
4. 原价、实时价格、总优惠金额和促销数量等汇总信息。

当前版本只开放“促销查询”。“优惠券查询”“价格巡检”“调度任务”和“历史会话”均只保留界面占位，不实现真实功能。

本项目虽然采用 AI 会话式布局，但不需要接入大模型，不需要实现自然语言理解，也不需要实现智能体自主工具调用。

## 五、总体架构

项目采用以下纯前端分层：

```text
React 页面与组件
        ↓
前端 Tool Router
        ↓
Mock Stream Service
        ↓
Promotion Mock Service
        ↓
本地 TypeScript / JSON 模拟数据
```

各层职责如下：

- 页面与组件层：负责布局、表单、会话消息、表格、结果卡片和状态展示。
- Tool Router：根据 `toolCode` 路由至对应模拟工具。
- Mock Stream Service：模拟后端流式分段返回。
- Promotion Mock Service：提供本地 SKU 全量促销查询、实时价格与命中促销查询。
- 本地数据层：提供站点、商品、促销、用户命中促销和异常场景数据。

页面组件不得直接读取底层模拟数据文件，必须通过 Service 层访问。

## 六、页面布局

### 6.1 整体布局

页面采用 AI 助手式双栏布局：

- 左侧：导航栏；
- 右侧：能力入口和会话交互区；
- 页面最小支持 1280×720 桌面端；
- 页面缩窄时布局不得出现大面积遮挡、错位或不可操作元素。

### 6.2 左侧导航栏

必须包含：

1. 营销百宝箱 LOGO 或文字标识；
2. “智能助手”菜单，默认选中；
3. “调度任务”菜单，置灰并标记“待开放”；
4. 历史会话模块占位，展示“暂无历史会话”或“功能暂未开放”；
5. 左侧栏展开/收起按钮；
6. 收起后仅保留图标或紧凑状态，右侧会话区自适应扩展；
7. 收起与展开过程不得导致页面内容溢出。

### 6.3 右侧顶部能力入口

顶部展示三个能力入口：

- 促销查询；
- 优惠券查询；
- 价格巡检。

要求：

1. “促销查询”为可用状态；
2. 另外两个能力显示“待开放”；
3. 点击“优惠券查询”或“价格巡检”时，在会话区增加提示卡片：
   - 标题：功能待开放；
   - 文案：该能力正在建设中，敬请期待；
4. 未开放能力不得触发模拟查询；
5. 能力入口下方显示固定提示：
   - 当前系统仅支持【促销查询】能力，其余功能持续迭代中。

## 七、促销查询交互

点击“促销查询”后，在会话区生成查询执行卡片。

### 7.1 输入项

必须包含以下必填项：

1. 站点选择：
   - 英国：1400；
   - 德国：1100；
   - 法国：1200；
   - 荷兰：1300。
2. SKU ID：
   - 文本输入；
   - 去除首尾空格；
   - 必填；
   - 最大长度 32。
3. 用户 PIN：
   - 文本输入；
   - 去除首尾空格；
   - 必填；
   - 最大长度 64。

### 7.2 按钮

查询卡片底部至少包含：

- 开始执行；
- 清空输入；
- 重新执行，仅在完成过一次查询后显示或可用。

要求：

1. 输入不完整时，点击开始执行应显示明确字段错误；
2. 请求执行期间，“开始执行”按钮进入加载状态并禁止重复提交；
3. 清空输入不得删除已经完成的历史结果；
4. 重新执行应使用上一次成功提交的参数重新发起一次模拟查询；
5. 用户可在查询结束后修改参数并继续执行新的查询。

## 八、模拟查询服务

促销查询由项目内的模拟服务完成，不调用真实网络接口。页面展示、本地数据和查询逻辑应合理分离，页面组件不直接承担数据查询与状态模拟逻辑。

查询分为两个连续阶段：

### 8.1 SKU 全量促销查询

使用站点和 SKU ID 查询：

- 商品基础信息；
- 当前站点；
- SKU 对应的全部促销列表；
- 有效促销数量；
- 查询时间；
- 查询状态。

### 8.2 实时价格与命中促销查询

使用站点、SKU ID 和用户 PIN 查询：

- 商品原价；
- 用户实时价格；
- 总优惠金额；
- 用户命中的促销列表；
- 币种；
- 计算时间；
- 查询状态。

### 8.3 能力路由

页面通过统一的业务入口发起促销查询，并由独立的业务模块调用相应的模拟查询服务。无法识别或尚未开放的能力返回明确的不可用状态。

## 九、模拟流式响应

不得一次性展示全部结果。必须使用 `AsyncGenerator`、异步迭代器或等效机制模拟分段返回。

一次正常查询至少依次产生以下事件：

1. `START`
2. `STATUS`：正在校验查询参数
3. `STATUS`：正在查询 SKU 全量促销
4. `ALL_PROMOTIONS`
5. `STATUS`：正在查询用户实时价格与命中促销
6. `REALTIME_PROMOTION`
7. `SUMMARY`
8. `DONE`

每个阶段应有可感知的延迟，建议每段 300—900 毫秒。延迟必须由模拟 Service 控制，不得在页面组件中散落多个定时器。

## 十、结果展示

每次执行应在会话区形成独立的一组会话内容，包括：

1. 用户查询摘要：
   - 站点；
   - SKU ID；
   - PIN，可部分脱敏展示；
2. 系统执行状态；
3. 全量促销信息；
4. 实时价格与命中促销；
5. 查询汇总；
6. 完成、空数据或错误状态。

### 10.1 全量促销表格

至少展示：

- 促销 ID；
- 促销名称；
- 促销类型；
- 原价；
- 优惠金额；
- 活动开始时间；
- 活动结束时间；
- 状态。

要求：

- 金额使用站点对应货币符号；
- 状态使用清晰标签；
- 无数据时展示空状态；
- 表格列不能被严重截断；
- 数据较多时支持分页或合理滚动。

### 10.2 实时价格与命中促销

至少展示：

- 商品名称；
- 商品原价；
- 实时价格；
- 总优惠金额；
- 命中促销数量；
- 计算时间；
- 命中促销明细。

价格展示中，实时价格应为视觉重点，但不得使用过度夸张的动画。

### 10.3 汇总信息

至少展示：

- 全量促销数量；
- 有效促销数量；
- 命中促销数量；
- 原价；
- 实时价格；
- 总优惠金额；
- 模拟查询耗时。

## 十一、本地业务数据

项目内置英国、德国、法国和荷兰四个站点的数据。

英国站点编码为 `1400`。商品 `100001` 的币种为 GBP，原价为 129.99，包含两条当前有效且促销 ID 不同的促销记录。使用不同用户查询该商品时：

- `test_user_01` 命中两条促销，实时价格为 99.99 GBP，总优惠金额为 30.00 GBP；
- `normal_user` 不命中促销，实时价格与原价相同；
- `unknown_user` 返回用户不存在状态；
- `partial_error_user` 可以取得商品及全量促销，实时价格查询返回部分失败状态；
- `error_user` 返回模拟接口异常；
- `timeout_user` 返回模拟超时状态。

德国站点编码为 `1100`。商品 `100003` 不包含促销，用户 `test_user_02` 查询时返回正常的无促销状态。

法国站点编码为 `1200`。商品 `100004` 包含多条促销，用户 `vip_user` 命中其中的有效促销。

荷兰站点编码为 `1300`。商品 `100005` 的促销数据中包含过期促销，用户 `test_user_03` 的查询结果区分有效和过期状态。

商品编号 `999999` 在所有站点均不存在。

促销记录包含促销 ID、名称、类型、优惠金额、开始时间、结束时间和状态。所有价格、促销数量及用户命中关系均来自项目内的本地业务数据，不随查询次数发生变化。README 中说明这些数据对应的查询状态。

## 十二、状态与异常处理

必须处理：

- 初始状态；
- 输入校验失败；
- 查询进行中；
- 正常成功；
- 无促销；
- 用户未命中任何促销；
- SKU 不存在；
- 用户不存在；
- 超时；
- 模拟接口异常；
- 全量促销成功但实时价格失败；
- 重复执行；
- 页面组件卸载时停止继续更新已经销毁的组件。

部分失败时，不得清空已经成功返回的全量促销结果。

## 十三、数据与安全展示要求

1. PIN 仅用于模拟查询。
2. 在用户查询摘要中对 PIN 进行部分脱敏，例如：
   - `test_user_01` 显示为 `te********01`。
3. 不得将 PIN 写入浏览器持久化存储。
4. 不使用 `localStorage`、`sessionStorage` 或 Cookie 保存查询记录。
5. 所有数据为模拟数据，页面中应明确标注：
   - “当前展示结果为模拟数据，不代表真实业务结果”。

## 十四、视觉与可用性要求

1. 整体风格应简洁、专业，符合企业内部工具。
2. 关键功能按钮、输入框、表格和错误状态具有清晰视觉层级。
3. 禁止通过大量渐变、荧光色或过度动画掩盖功能缺失。
4. 按钮、输入框和菜单均应具备 hover、focus、disabled 状态。
5. 页面在常见桌面浏览器中无明显布局错误。
6. 左侧栏折叠后，右侧内容宽度应正确更新。
7. 会话内容较多时，用户应能正常浏览已有结果。
8. 动态状态区域应提供适当的 `aria-live` 或等效可访问性支持。
