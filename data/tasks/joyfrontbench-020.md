二级分类：移动端应用界面

请你扮演一名资深产品型前端工程师，设计并实现一个高完成度的移动端金融交易 App 仪表盘。页面要放在一个真实感手机外框里，看起来像可以交付给用户使用的消费金融产品，而不是静态展示稿。

交付形式必须是一个可运行的多文件前端工程，而不是单个 HTML 文件。请使用 Vite + React + TypeScript 实现；图标、图表可以使用轻量 npm 依赖，也可以使用 CSS/SVG/Canvas 自绘。允许 npm 安装和构建，但禁止 API 请求、外部图片素材和远程运行时数据。

工程结构要求：

1. 必须包含 package.json、index.html、src/main.tsx、src/App.tsx、README.md。
2. package.json 至少提供：
   - npm run dev
   - npm run build
   - npm run test
   - npm run lint 或 npm run typecheck
3. 至少拆分出以下职责模块，不要把主要逻辑堆在 App.tsx：
   - 交易数据、账户数据、银行卡数据和 TypeScript 类型
   - 全局 UI 状态、筛选状态和自定义 hooks
   - 手机外框、状态栏、安全区和底部导航
   - 余额概览和现金流摘要
   - 卡片轮播或分段卡片选择器
   - 快捷操作
   - 搜索、月份选择和筛选 chips
   - 最近交易列表和虚拟化或分组渲染策略
   - 交易详情底部抽屉
   - 转账表单底部抽屉
   - 消费图表、现金流图表和分类明细
   - 预算进度和分类预算
   - localStorage 持久化工具
   - 表单校验和数据派生工具函数
5. 交易筛选、搜索、月份聚合、收入支出统计、分类汇总、预算百分比、图表数据生成、转账表单校验必须放在可测试的纯函数里。
6. 类型定义要清晰，Transaction、CardAccount、ThemeMode、FilterChip、MonthlySummary、CategorySummary、BudgetState、TransferFormState、SheetState 等核心数据要有 TypeScript 类型。
7. 不允许把所有交易和所有 UI 文案混在组件 JSX 中；数据、派生逻辑、展示组件和交互容器要分层。
8. 不允许使用 dangerouslySetInnerHTML，不允许把完整页面或大段组件写成字符串模板。

核心 UI 要求：

1. 展示真实感手机框架，包括状态栏、灵动岛或刘海、安全区间距、内部滚动容器和底部导航。
2. App 内必须包含：
   - 账户余额概览
   - 本月收入、支出、净额和环比变化
   - 主支付卡片
   - 第二张储蓄卡或钱包卡片
   - 快捷操作
   - 最近交易列表
   - 消费洞察
   - 预算进度
   - 分类消费明细
   - 即将扣款或订阅提醒
3. 至少准备 24 条真实感交易样例，覆盖购物、收入、餐饮、交通、订阅、旅行、转账、医疗、教育等多个分类，并且至少覆盖 4 个月份。
4. 交易数据必须包含 pending、settled、refunded 三种状态中的至少两种，详情抽屉要展示状态。
5. 收入和支出要有清晰的正负号、颜色区分和分类图标。
6. 卡片必须展示主卡和储蓄/钱包卡两种不同视觉样式，卡号、有效期、持卡人和余额都要稳定排版。持卡人必须使用统一的虚构姓名 Alex Morgan，卡号、有效期、余额和所有账户/交易数据一律为虚构示例，不得出现任何真实人物、真实姓名、真实卡号或出题人身份信息。

交互要求（每条交互都必须是完整闭环，不允许“半截交互”）：

通用原则：

1. 闭环要素：每条交互都要走完“触发反馈（按压或加载态）→ 校验（如需要）→ 状态变更 → 相关派生数据与视图同步更新 → 成功/失败的可见反馈”，涉及用户偏好或数据变更的还要写入 localStorage；不允许出现点了没反应的“死控件”，无法使用的功能要以明确的禁用或“即将上线”态呈现。
2. 单一数据真源：列表、顶部统计、图表、分类明细、预算、卡余额都从同一份“可见交易”派生，任何时刻不得出现彼此矛盾的中间态（如图表变了但顶部数字没变）。“可见交易”口径统一为“当前月份 + 当前筛选 + 当前搜索”；分类预算按“当前月份”支出计算、不随搜索关键字变化。该口径需在 README 说明并全站一致。
3. 抽屉/弹层通用：打开时焦点进入其中、Tab 不逸出，Escape 与点击遮罩均可关闭，关闭后焦点回到触发元素、不遗留被锁定的页面滚动；会提交数据的操作（如转账确认）必须防重复提交——提交中禁用并显示进行中态，连点不产生多条记录。

各交互链路（每条只需实现一次，均须闭环）：
4. 搜索：输入 → 约 200ms debounce → 按 merchant/category/note/method 重算可见交易 → 列表、图表、统计、分类明细同步刷新；搜索框带清除按钮；无结果显示空状态并提供“清空搜索”入口，点击即恢复未搜索态。
5. 筛选 chips（全部/收入/支出/餐饮/购物/转账/订阅）：点击或键盘左右方向键切换选中态、同步 aria-pressed（选中项 true、其余 false）；与搜索可叠加取交集、互不重置；无匹配显示空状态并提供“切回全部”入口。
6. 月份选择器：切换后顶部总额/本月收支/环比、现金流摘要、预算进度、分类明细、订阅提醒与两张图表全部随所选月份同步刷新，且同源于当月可见交易、口径一致；切到无数据月份呈空态并归零。
7. 交易详情抽屉：整行可点且有按压态 → 打开抽屉展示商户、分类、日期、金额、支付方式、状态、备注全字段（遵循通用抽屉焦点规则）。
8. 详情内轻量操作——复制交易编号：点击复制到剪贴板并显示“已复制”反馈；在不支持或无权限（如非 HTTPS）的环境要有回退（选中文本或提示手动复制）并给失败反馈，绝不静默失败或抛未捕获异常。标记/编辑备注：保存后备注真实回写数据真源，列表行与详情同步显示、可被搜索命中、写入 localStorage 刷新后仍在，并给“已保存”反馈；失败要有反馈且不破坏原备注。
9. 银行卡——卡片切换：轮播或分段选择器（有按压态）切换当前卡并写入 localStorage；当前卡统一驱动卡片详情、卡号显隐目标、转账默认支付卡与余额校验目标。卡号显隐：开关在掩码与完整卡号间切换、对当前卡生效、状态写入 localStorage 刷新恢复。
10. 转账（完整交易链路）：点“转账”打开抽屉，填收款人、金额、备注、选支付卡 → 字段级校验（金额需校验空值、非数字、负数、超所选卡余额，错误显示在对应字段旁而非仅 alert）→ 二次确认（防重复提交）→ 成功后：立即生成一条结构完整、符合 Transaction 类型的新交易（稳定且不重复的 id、分类固定为“转账”、方向为支出且金额为负、支付方式为所选卡、状态可见、备注为用户所填 note）并按时间倒序置顶插入最近交易列表；同时扣减所选卡余额，账户总额、本月收支/净额/环比、现金流摘要、两张图表、分类明细（含“转账”占比）、分类预算全部即时重算，且金额统一走格式化工具；新交易参与搜索/筛选、可点开详情、写入 localStorage 刷新后仍在；全程不得出现“扣了余额但列表没有”“列表有但统计没算”一类矛盾。写回逻辑（构造交易、插入列表、扣减余额、重算派生）须放在可测试的纯函数或 reducer 中，不写死在点击回调里。
11. 快捷操作：“转账”走上述转账链路；其余（收款/扫码/充值/账单等）要么实现真实轻量流程/抽屉并给反馈，要么呈明确禁用/“即将上线”态，不留假按钮。
12. 底部导航：点击切换到对应视图或锚点并高亮当前项；未实现的页签以禁用/占位清晰呈现，不做纯装饰死图标。
13. 订阅/即将扣款：按明确规则从当前月份派生（如晚于今天且属于本月的周期性支出）→ 随月份切换同步更新 → 每条可点开详情（周期、金额、下次扣款日、关联卡）→ 若提供“立即支付”，须复用转账链路生成真实交易并联动，不允许只是静态文案。
14. 偏好持久化：主题、当前卡片、卡号显隐、最近使用月份等偏好写入 localStorage，刷新后自动恢复；读写要容错，坏值/非法 JSON 要退回安全默认、不导致页面崩溃。

数据可视化要求：

1. 用 CSS、SVG 或 Canvas 绘制消费图表，禁止写死图形。
2. 至少包含一个本月支出趋势图和一个收入/支出现金流对比图，可以组合在同一图表区域，也可以分成两个图表。
3. 月份、搜索或筛选状态变化时，图表必须更新。
4. 增加分类消费明细行，包含分类名称、金额、占比和进度条。
5. 增加分类预算进度，至少包含餐饮、购物、交通、订阅四类预算。
6. 搜索或筛选没有结果时必须显示空状态，而不是空白区域。
7. 图表数据生成要来自当前可见交易，不允许写死。
8. 数字格式要统一使用工具函数，不能在多个组件中重复手写金额格式化逻辑。

设计和响应式要求：

1. 页面在移动端宽度下可用，在桌面端也要居中且保持精致。
2. 手机屏幕内部内容要能自然滚动，不能撑破手机外框。
3. 卡片、底部导航、筛选器、交易行、图表区域和抽屉都要有稳定尺寸。
4. 文字不能在按钮、卡片、列表行或底部抽屉中重叠、溢出或被裁切。
5. 控件要适合触摸操作，并且有清晰 focus 状态和可访问对比度。
6. 必须提供亮色模式和深色模式，并用真正的主题切换器控制。
7. 不要做成单一紫色调界面，要使用适合金融产品的平衡色彩系统，并有明确语义色。
8. reduced-motion 模式下要关闭非必要入场动画和抽屉大幅位移，但功能仍可用。

动效和细节要求：

1. 页面头部、卡片、快捷操作、图表和交易列表需要有克制的入场动画。
2. 按钮、chips、交易行和卡片切换要有触感明确的按压状态。
3. 底部抽屉的打开和关闭要有平滑动画。
4. 数据变化时，统计数字、图表和预算条要有轻微过渡，但不能造成布局跳动。
5. 必须尊重 prefers-reduced-motion。

工程质量要求：

1. npm run dev 能启动页面，npm run build 必须通过。
2. npm run test 必须通过。
3. npm run lint 或 npm run typecheck 必须通过。
4. 浏览器控制台不能有运行时报错、资源 404 或 React key/状态警告。
5. React 组件要有稳定 key，不允许用数组下标作为交易列表 key。
6. 派生数据要用 memo 或纯函数合理组织，不能在多个组件中重复计算且结果不一致。
7. localStorage 读写要有容错处理，坏值不能导致页面崩溃。
8. 表单校验逻辑要可复用，不要只写在点击事件里。
9. README.md 必须说明运行、构建、测试、主要模块职责和已知限制。
